1. A virtual environment solves the problem of different projects needing different Python packages or versions without interfering with one another or with the system Python.

The command that creates one:

python3 -m venv .venv

After activation, running:

which python

showed a path inside my project’s virtual environment, such as:

.../project/.venv/bin/python

That proved the shell was using the virtual environment’s Python interpreter rather than the system-wide one.

2. My .gitignore contains:

.venv/
__pycache__/
.DS_Store

.venv/ tells Git to ignore the project’s virtual-environment folder.
__pycache__/ tells Git to ignore Python’s automatically generated bytecode-cache files.
.DS_Store tells Git to ignore the hidden metadata files macOS creates inside folders.

You do not commit .venv/ because it is large, machine-specific, and can be rebuilt from the project’s dependency list. You commit the source code and dependency instructions—not an entire local Python installation.

3. 
A pure function gets everything it needs through its parameters, computes a result, and returns that result without changing anything outside itself.

For example:

def count_degrees(edges):
    degree = {}
    # compute degrees
    return degree

For the same edges, it gives the same result. It does not print, alter global variables, or modify the input list.

A module should avoid top-level print() because top-level code executes immediately when the module is imported:

import helpers

If helpers.py contained:

print("hello")

then "hello" would appear merely because another program imported the module. That's an unwanted side effect.

So the principle is:

Reusable modules should define functions and return results; they should not unexpectedly perform actions just because they were imported.

6. 
def parse_edge_file(path):
    good_edges = []
    bad_rows = []

    with open(path) as f:
        for line in f:
            line = line.strip()

            try:
                parts = line.split(",")

                if len(parts) != 2:
                    raise ValueError("wrong number of fields")

                u = int(parts[0])
                v = int(parts[1])

                good_edges.append((u, v))

            except (ValueError, IndexError):
                bad_rows.append(line)

    return good_edges, bad_rows

The key structure is:

try:
    parse and convert a valid row
except:
    collect the bad row instead of crashing

And the explicit len(parts) != 2 check catches malformed rows like 7 that would otherwise slip through without raising an exception.

7. try/except alone is not enough because it only catches something when Python actually raises an exception.

With your file:

0,1
1,2
2,3
1,3
5
a,b
7,8,9

before the field-count check, the row:

7,8,9

could still be processed using its first two values:

u = int(parts[0])   # 7
v = int(parts[1])   # 8

Both conversions succeed, so the parser would incorrectly accept it as:

(7, 8)

The extra 9 would be ignored. Since nothing failed, except had nothing to catch.

The fix is the explicit structural check:

if len(parts) != 2:
    raise ValueError("wrong number of fields")

Now the rows behave like this:

0,1     → valid → (0, 1)
1,2     → valid → (1, 2)
2,3     → valid → (2, 3)
1,3     → valid → (1, 3)
5       → bad: only 1 field
a,b     → bad: "a" and "b" cannot convert to int
7,8,9   → bad: 3 fields instead of exactly 2

So the important distinction is:

try/except catches operations that fail; the len(parts) != 2 check catches input that is structurally wrong even though Python could otherwise process it.

7,8,9 is the classic silent validation/logic bug: without the length check, bad input can produce a perfectly plausible-looking result.

read_edges.py and helpers.py are the modules; analyze_graph.py is the script you run directly.

read_edges.py — parser module. It opens edges.txt, cleans and validates each row, converts valid rows into integer edge tuples, and returns good_edges and bad_rows.
helpers.py — analysis module. It takes the valid edges, computes the vertex-degree dictionary, and checks which vertices exceed their capacities.
analyze_graph.py — main script. It imports both modules, calls their functions in the correct order, receives their returned data, and prints the final report.

For one valid row such as 0,1, the full data flow is:

edges.txt
   ↓
"0,1\n"
   ↓
read_edges.parse_edge_file()
   ↓
strip → split → validate → convert
   ↓
(0, 1)
   ↓
good_edges
   ↓
analyze_graph.py
   ↓
helpers.count_degrees(good_edges)
   ↓
degrees dictionary
   ↓
helpers.find_over_capacity(degrees, capacity)
   ↓
over-capacity list
   ↓
analyze_graph.py
   ↓
final printed report

So the simplest mental model is:

read_edges.py turns text into clean data → helpers.py analyzes that data → analyze_graph.py coordinates the two and prints the results.
